# Упражнения: что делать дальше самому

Проект — не музейный экспонат, а тренажёр. Ниже упражнения по возрастанию сложности. У каждого есть критерий «готово» и подсказка, куда смотреть.

Делай по одному и **коммить каждое отдельно** — заодно отработаешь работу с git.

---

## Уровень 1. Освоиться

### 1.1. Прогнать всё и прочитать отчёт

Запусти `1 Все тесты`, затем `7 Отчёт Allure`. Найди в отчёте дерево шагов — те самые `@Step`.

**Готово, когда:** можешь объяснить, чем отчёт Allure полезнее панели Run в IDE.

### 1.2. Сломать тест намеренно

В `AccountsListTest` в проверке колонок поменяй `"Name"` на `"Название"`. Запусти. Посмотри текст ошибки, открой скриншот из отчёта. Верни обратно.

**Готово, когда:** понимаешь, как по сообщению об ошибке найти причину, и знаешь, где лежит скриншот падения.

### 1.3. Добавить компанию в параметризованный поиск

В `AccountsListTest` в `@ValueSource` добавь четвёртую компанию из списка на стенде.

**Готово, когда:** в отчёте четыре строки вместо трёх, все зелёные.

## Уровень 2. Писать проверки

### 2.1. Тест на колонки другого раздела

Открой на стенде раздел **Contacts**. Напиши `ContactsListTest` по образцу `AccountsListTest`: проверь колонки и сверь счётчик с API.

**Подсказка.** Адрес раздела — `#Contact`. Структура разметки та же: `tr.list-row`, `th.field-header-cell[data-name=...]`. Понадобится новый Page Object. Метод API — по аналогии с `accountsTotal()`, только путь `/Contact`.

**Готово, когда:** тест зелёный и в Page Object нет ни одной проверки.

### 2.2. Проверка сортировки

В списке компаний кликни по заголовку «Name» — список отсортируется. Напиши тест, который это проверяет.

**Подсказка.** Сортировка — ссылка `a.sort[data-name='name']` внутри заголовка. Получить все названия можно через `accountNames().texts()` — вернётся `List<String>`. Сравнить с отсортированной копией поможет AssertJ: `assertThat(list).isSorted()`.

**Готово, когда:** тест ловит обратный порядок — проверь, поменяв `isSorted()` на проверку обратной сортировки.

### 2.3. Редактирование компании

Создай компанию через API, открой её карточку в интерфейсе, измени название, сохрани. Проверь результат через API. Убери за собой.

**Подсказка.** Адрес карточки — `#Account/view/{id}`. Кнопка редактирования — `[data-action="edit"]`. Идентификатор вернёт `EspoApi.createAccount(name)`.

**Готово, когда:** тест не оставляет мусора даже при падении — проверь, сломав проверку намеренно.

## Уровень 3. Расширять фреймворк

### 3.1. Вынести общие ожидания

Заметь, что `shouldBe(visible, Duration.ofSeconds(20))` повторяется во многих местах. Вынеси таймаут в константу или настройку.

**Готово, когда:** магическое число 20 не встречается в коде ни разу.

### 3.2. Свой тип проверки для таблицы

Напиши метод, проверяющий, что в строке с заданным названием компании в колонке «Type» стоит нужное значение.

**Подсказка.** В `AccountsListPage` уже есть заготовка — метод `cell(accountName, columnName)`.

**Готово, когда:** проверка умещается в одну строку теста и читается как фраза.

### 3.3. Тест с подготовкой данных через API

Создай через API пять компаний с общим префиксом в названии, найди их поиском в интерфейсе, проверь, что нашлось ровно пять, удали все.

**Подсказка.** Удалять удобно в `@AfterEach`, накопив идентификаторы в `List<String>`.

**Готово, когда:** тест стабильно проходит пять раз подряд — это и есть проверка на самоочистку.

## Уровень 4. Инфраструктура

### 4.1. Параллельный запуск

Включи в `junit-platform.properties`:

```properties
junit.jupiter.execution.parallel.enabled=true
junit.jupiter.execution.parallel.mode.default=concurrent
```

Запусти всё. Скорее всего, что-то сломается.

**Готово, когда:** можешь объяснить, почему Selenide хранит WebDriver в `ThreadLocal` и какие тесты при параллельном запуске мешают друг другу. Это частый вопрос на собеседованиях.

### 4.2. Разобрать автоматический прогон

Прогон на GitHub уже настроен и зелёный — значок виден в README. Задача не настроить его, а **понять**.

Открой `.github/workflows/tests.yml` и ответь себе на вопросы: почему пароли заданы прямо в файле и почему это безопасно именно здесь; зачем файлы настроек создаются на лету, а не лежат в репозитории; почему скриншоты сохраняются только при падении.

Затем сломай что-нибудь намеренно: поменяй в любом тесте ожидаемое значение, запушь и посмотри, что покажет GitHub. Обрати внимание на аннотацию с названием упавшего теста — именно для этого в прогон добавлен шаг «Показать упавшие тесты». Верни обратно.

**Готово, когда:** можешь объяснить, почему прогон падал с кодом 126 до исправления. Подсказка — в коммите `5358a42`:

```bash
git show 5358a42
```

### 4.3. Новая сущность целиком

Выбери раздел, которого ещё нет в тестах — Opportunities или Leads. Покрой его полностью: список, создание, валидация, API, сверка с базой.

**Готово, когда:** новый раздел покрыт так же, как компании, и код не дублирует существующий, а переиспользует общие части.

## Чего избегать

Это ошибки, которые делают почти все начинающие. Если поймаешь себя — переделай.

**`Thread.sleep` вместо ожидания условия.** В этом проекте нет ни одного, и это принципиально. Фиксированная пауза либо коротка, либо длинна, и всегда не вовремя.

**Проверки в Page Object.** Он находит и действует. Решает тест.

**Жёстко вписанные данные.** Количество записей, идентификаторы, даты — спрашивай у системы.

**Тест, зависящий от другого теста.** Каждый должен проходить в одиночку и в любом порядке. Проверить легко: запусти один тест отдельно.

**Тест без уборки.** Создал — удали, даже если упал.

**Локатор по сгенерированному классу.** `css-1m748n2` сменится при следующей сборке фронтенда.

А этот репозиторий к тому моменту станет готовым портфолио: ссылку можно класть в резюме. Главное — не просто иметь его, а уметь объяснить на собеседовании **каждое решение** в нём. Для этого и написан разбор кода.
