# Разбор кода: слой за слоем

Проект устроен слоями. Каждый слой знает только о соседнем снизу и ничего — о том, кто его использует. Благодаря этому изменение в одном месте не расползается по всему проекту.

```
Тест            «создай компанию и проверь, что она сохранилась»
  ↓
Steps           «создай компанию» = открой список → нажми Создать → заполни → сохрани
  ↓
Page Object     «заполни поле Название» = найди input[data-name=name] и введи текст
  ↓
Selenide        работа с браузером
```

Рядом стоят два слоя, которые с браузером не связаны: **API** (REST Assured) и **БД** (JDBC). Они нужны и как объект проверки, и как быстрый способ подготовить или убрать данные.

---

## Слой 1. Конфигурация — `config/TestConfig.java`

Единственное место, где проект знает адрес стенда и пароли.

```java
Configuration.baseUrl = TestConfig.url();
```

Три решения, которые стоит перенять:

**Настройки читаются один раз.** Поле `private static final Properties PROPS = load()` инициализируется при первом обращении к классу и дальше живёт в памяти.

**Системное свойство перебивает файл.** Поэтому можно запустить с другим адресом, ничего не редактируя:

```bash
gradlew test "-Durl=http://localhost:9090"
```

**Отсутствие настройки — это немедленное падение с объяснением**, а не `NullPointerException` где-то в глубине теста:

```
В файле env/local.properties не задан параметр 'adminPass'.
Скопируй env/local.properties.example в env/local.properties и заполни значения.
```

Пароли лежат в `local.properties`, который **в git не попадает** — он в `.gitignore`. В репозитории только шаблон `local.properties.example`. Это обязательная практика: пароль, попавший в публичный репозиторий, считается скомпрометированным навсегда, даже если удалить его следующим коммитом — он останется в истории.

## Слой 2. База UI-тестов — `common/BaseUiTest.java`

Абстрактный класс, от которого наследуются все UI-тесты. Делает три вещи.

**Настраивает Selenide** — адрес, размер окна, таймаут ожидания.

**Подключает отчёт.** Слушатель `AllureSelenide` перехватывает каждое действие и кладёт его в отчёт отдельным шагом, а при падении автоматически прикладывает скриншот и исходный код страницы. Без него в отчёте был бы только текст ошибки.

**Закрывает браузер после каждого теста** — и это главное решение здесь:

```java
@AfterEach
void closeBrowser() {
    closeWebDriver();
}
```

Почему после каждого, а не раз на класс: так тесты изолированы. Каждый начинается с чистой сессии, без куков и состояния от предыдущего. Тест, падающий из-за соседа, — худший вид нестабильности, он отнимает часы на поиск несуществующей ошибки.

Платим временем на перезапуск браузера. Это осознанный размен в пользу надёжности.

> **Чем это отличается от рабочего проекта.** В `cometal` драйвер закрывается так же, но там это привело к ограничению: нельзя сделать «авторизоваться один раз и проверить десять шагов». Пришлось складывать все проверки в один тестовый метод. Понимание этой связи между устройством базового класса и дизайном тестов — ровно то, что отличает инженера от исполнителя.

## Слой 3. Page Objects — `pages/`

Описание страницы: где лежат элементы и что с ними можно делать.

**Главное правило: в Page Object нет проверок.** Он находит элементы и выполняет действия. Решает, что считать правильным, — тест. Если смешать, один и тот же объект нельзя будет использовать и в позитивном, и в негативном сценарии.

### Локаторы

Все локаторы опираются на `id` или `data-name`:

```java
private final SelenideElement nameInput =
        $("div.field[data-name='name'] input[data-name='name']");
```

`data-name` — собственный атрибут EspoCRM, которым помечено каждое поле. Такой локатор читается как название поля в интерфейсе и переживает смену вёрстки.

Чего избегать: привязки к сгенерированным CSS-классам (`css-1m748n2` сменится при следующей сборке фронтенда) и к позиции элемента (`div > div:nth-child(3)` сломается от любой вставки).

### Коллекции — ленивые

```java
private final ElementsCollection rows = $$("tr.list-row");
```

`ElementsCollection` не обращается к браузеру, пока её не спросят. Разница принципиальна:

```java
rows.shouldHave(size(15));   // будет перепроверять, пока таблица догружается
rows.size();                 // вернёт сколько есть ПРЯМО СЕЙЧАС — на медленной загрузке ноль
```

Вторая строка — типичная причина «плавающих» падений.

### Выпадающие списки

EspoCRM рисует их библиотекой Selectize: настоящий `<select>` скрыт (`display: none`), а пользователь видит набор div-ов. Обычный `selectOption()` по скрытому select не сработает. Поэтому работаем как человек:

```java
public AccountFormPage selectType(String type) {
    $("div.field[data-name='type'] .selectize-input").click();
    $$(".selectize-dropdown [data-value='" + type + "']").first().shouldBe(visible).click();
    return this;
}
```

Обрати внимание: меню рисуется **не внутри поля**, а отдельным блоком, поэтому пункт ищется глобально.

## Слой 4. Steps — `steps/`

Переводит язык интерфейса на язык задачи.

Page Object говорит: «введи текст в поле», «нажми кнопку». Тест должен говорить: «войди администратором». Steps — переводчик между ними.

```java
@Step("Войти под администратором")
public void loginAsAdmin() {
    loginAs(TestConfig.adminLogin(), TestConfig.adminPassword());
}
```

Польза двойная:

1. Когда форму входа переделают и шагов станет четыре вместо двух, поменяется **один метод**, а не двадцать тестов.
2. Отчёт Allure читается как сценарий из тест-кейса, а не как протокол кликов.

Аннотация `@Step` работает только при подключённом AspectJ-агенте — он настроен в `build.gradle` плагинами Allure. Без агента аннотации молча игнорируются и отчёт выходит пустым.

### Ожидания привязаны к данным, а не к разметке

```java
public AccountsListPage openList() {
    listPage.openPage();
    listPage.rows().shouldBe(sizeGreaterThan(0), Duration.ofSeconds(20));
    return listPage;
}
```

В одностраничном приложении разметка появляется мгновенно, а данные приезжают отдельным запросом. Ждать «страница открылась» бессмысленно — надо ждать «строки появились».

**`Thread.sleep` в этом проекте нет ни одного, и это принципиально.** Selenide сам перепроверяет условие, пока оно не выполнится или не истечёт таймаут. Фиксированная пауза либо слишком коротка (тест падает), либо слишком длинна (прогон тянется часами) — и всегда ровно тогда, когда не надо.

## Слой 5. API — `api/EspoApi.java`

Обёртка над REST Assured. Общая часть всех запросов собрана в спецификацию:

```java
public static RequestSpecification authorized() {
    return new RequestSpecBuilder()
            .setBaseUri(TestConfig.url())
            .setBasePath("/api/v1")
            .setContentType(ContentType.JSON)
            .addHeader("Authorization", "Basic " + basic)
            .addHeader("X-Skip-Duplicate-Check", "true")
            .build();
}
```

Заголовок `X-Skip-Duplicate-Check` отключает встроенную проверку дублей: без него создание записи с существующим названием отвечает `409 Conflict`.

Два правила использования API в тестах:

**Подготовка данных — через API, проверка — через то, что тестируем.** Создать компанию через API — секунда, через интерфейс — пятнадцать. Если тест проверяет не создание, а что-то другое, данные нужно готовить самым быстрым способом. Но если тест про создание в интерфейсе — создавать надо именно в интерфейсе.

**Уборка не должна ронять тест.** Поэтому удаление «тихое»:

```java
public static void deleteAccountQuietly(String id) { ... }
```

Если запись не удалилась — это проблема стенда, а не проверяемой функциональности. Валить из-за неё зелёный тест неправильно.

## Слой 6. База — `db/Database.java`

Самый глубокий уровень проверки. Интерфейс может нарисовать запись из кэша, API — отдать её из промежуточного слоя, а в таблице её не окажется.

Два приёма в коде:

**try-with-resources.** Соединение, запрос и результат объявлены в скобках после `try` — Java закроет их сама, даже при исключении. Забытое соединение это утечка: через сотню тестов база перестанет принимать подключения.

**PreparedStatement вместо склейки строк.** Значения подставляются через `?`:

```java
statement = connection.prepareStatement("SELECT name FROM account WHERE id = ?");
statement.setString(1, id);
```

Это защищает от SQL-инъекции и снимает вопрос экранирования кавычек — а в наших тестовых компаниях кавычки есть: `АО «Метиз-Трейд»`.

## Слой 7. Тесты — `tests/`

Разделены по пакетам `ui`, `api`, `db` и помечены тегами для выборочного запуска.

### Что проверять, кроме счастливого пути

Из пяти API-тестов три — негативные: отказ без авторизации, отказ без обязательного поля, отказ при дубле. Это не перебор. Счастливый путь обычно проверяют и разработчики, и ручное тестирование. А вот что система делает с неверным запросом — забывают, и именно там живут дефекты.

### Сверка независимых источников

```java
int totalFromApi = EspoApi.accountsTotal();
list.counter().shouldHave(attributeMatching("title", "Total: " + totalFromApi));
```

Тест не знает заранее, что компаний пятнадцать — он спрашивает систему. Жёстко вписанное число ломается, как только кто-то добавил запись на стенде.

### Уборка за собой

```java
@AfterEach
void removeCreatedAccount() {
    EspoApi.deleteAccountQuietly(createdAccountId);
}
```

`@AfterEach` выполняется **даже если тест упал**. Без этого после сотни прогонов в стенде будет сотня мусорных компаний, и проверки количества начнут падать на ровном месте.

### Параметризованные тесты

```java
@ParameterizedTest(name = "Поиск находит компанию: {0}")
@ValueSource(strings = {"ООО «УралПрокат»", "АО «Метиз-Трейд»", "ООО «ЭнергоСвар»"})
void searchFindsAccount(String companyName) { ... }
```

Один код, три набора данных, три отдельные строки в отчёте. Упадёт одно значение — остальные всё равно выполнятся, и будет видно, какое именно сломалось.

## Две находки, которые сделали тесты

Это не выдуманные примеры — обе обнаружились при написании этого кода.

### Интерфейс обрезает схему у адреса сайта

Ввели `https://autotest.example.ru` — на сервере сохранилось `autotest.example.ru`. Проверка через API показала, что **схема сохраняется**, значит обрезает её именно виджет формы.

Правильная реакция: не «подогнать тест», а разобраться и зафиксировать фактическое поведение с объяснением в комментарии. В реальной работе дальше идёт вопрос команде: так задумано или дефект?

### Удаление мягкое

Изначально тест проверял, что после удаления запись отдаёт `404`. Он падал, хотя система работала правильно. Разбор показал настоящий контракт:

| Что происходит | Как видно |
|---|---|
| Запись остаётся в базе | `SELECT` находит строку |
| Выставляется признак | `deleted = 1`, API отдаёт `"deleted": true` |
| Из списков исчезает | `total` уменьшается |
| По идентификатору читается | `GET /Account/{id}` → `200` |

Отсюда практическое следствие, которое теперь живёт в коде: любой SQL-запрос, сверяющий данные с интерфейсом, обязан содержать `WHERE deleted = 0`.

**Вывод, который стоит запомнить:** красный тест не всегда означает дефект в системе. Иногда он означает, что ты неверно понял, как система работает. Разбираться надо всегда.
