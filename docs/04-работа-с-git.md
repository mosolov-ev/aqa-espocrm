Здесь разобрано, как именно собиралась история этого репозитория — и как повторять это самому.

## Устройство: три места, где живёт код

| Где | Что это | Зачем |
|---|---|---|
| Рабочая папка | `C:\Users\Evgeny\IdeaProjects\aqa-espocrm` | здесь ты редактируешь файлы |
| Локальный репозиторий | папка `.git` внутри проекта | вся история коммитов, на твоём диске |
| Удалённые репозитории | `origin` на GitHub, `local` на диске D: | копии для сохранности и обмена |

Ключевое, что часто понимают не сразу: **git работает полностью локально**. Коммиты делаются без интернета и без сервера. Удалённый репозиторий нужен только чтобы делиться кодом и не потерять его вместе с диском.

В проекте настроено два удалённых:

```bash
git remote -v
```

```
local   D:/git-remotes/aqa-espocrm.git
origin  https://github.com/mosolov-ev/aqa-espocrm.git
```

`local` — обычная папка на диске D:, работает всегда, без интернета, VPN и аккаунтов. `origin` — GitHub, он же портфолио.

## Ежедневный цикл

Четыре команды, которые покрывают 90% работы.

**Посмотреть, что изменилось:**

```bash
git status
```

**Добавить изменения в будущий коммит:**

```bash
git add .
```

Точка означает «всё в текущей папке и ниже». Можно добавить один файл: `git add src/test/java/ru/espocrm/pages/LoginPage.java`.

**Зафиксировать:**

```bash
git commit -m "Тест поиска по списку компаний"
```

**Отправить на сервер:**

```bash
git push
```

Всё это есть и в IntelliJ: меню **Git → Commit** (Ctrl+K) и **Git → Push** (Ctrl+Shift+K). Пользуйся чем удобнее — результат одинаковый.

Три принципа, по которым они написаны:

**Один коммит — одна законченная мысль.** Не «работа за вторник», а «слой конфигурации». По такой истории видно, как рос проект, и любой коммит можно откатить отдельно.

**Первая строка — что сделано, коротко.** До 70 символов, без точки в конце. Это то, что видно в `git log --oneline` и на GitHub.

**В теле — почему так, а не как.** Что сделано, видно из кода. Из кода не видно, почему выбран именно этот путь. Посмотри развёрнуто:

```bash
git show 4dd9127
```

Там объяснено, почему негативных тестов больше позитивных и почему пришлось добавить `jackson-databind`. Через полгода ты не вспомнишь — а коммит помнит.

Плохие сообщения, которых стоит избегать: `fix`, `работа`, `update`, `тесты`. Они не несут информации, и история из таких коммитов бесполезна.

## Ветки

В проекте есть один показательный пример. Посмотри граф:

```bash
git log --oneline --graph -8
```

```
*   c6319ef Влитие ветки feature/account-name-validation
|\
| * 85b250b Тест валидации: компания без названия не сохраняется
|/
* 73949a9 Конфигурации запуска для IntelliJ IDEA
```

Видна «вилка»: работа ушла в отдельную ветку и вернулась обратно. Вот как это делалось.

**Создать ветку и перейти в неё:**

```bash
git checkout -b feature/account-name-validation
```

Имя по соглашению: `feature/` для новой работы, `fix/` для исправления, дальше суть латиницей через дефис.

**Поработать и закоммитить** — как обычно, `git add` и `git commit`.

**Вернуться в основную ветку:**

```bash
git checkout main
```

**Влить:**

```bash
git merge --no-ff feature/account-name-validation -m "Влитие ветки feature/account-name-validation"
```

Ключ `--no-ff` здесь важен. Без него git просто «перемотал» бы ветку вперёд, и в истории не осталось бы следа, что работа велась отдельно. С ним создаётся отдельный коммит слияния — именно так выглядит история в командной работе через merge request.

**Удалить влитую ветку:**

```bash
git branch -d feature/account-name-validation
```

### Зачем это нужно на работе

В `cometal` ты работал в ветке `TEST-CLAUDE-2` — это тот же механизм. В команде в `main` или `dev` напрямую обычно не коммитят: работа идёт в ветке, затем открывается merge request, коллега смотрит код, и только потом ветка вливается. Умение жить в ветках — обязательный навык, и здесь он отработан на своём проекте.

## Что НЕ попадает в репозиторий

Файл `.gitignore` описывает исключения:

```
build/                                      результаты сборки
.gradle/                                    служебные файлы Gradle
.idea/                                      личные настройки IDE
allure-results/                             сырые данные отчёта
src/test/resources/env/local.properties     ПАРОЛИ
stand/.env                                  ПАРОЛИ
stand/backup/*.sql.gz                       снимки базы
!stand/backup/espocrm-seed.sql.gz           кроме эталонного дампа
```

Две последние строки — пример исключения из исключения: все дампы игнорируются, кроме эталонного, который нужен для развёртывания.

**Про пароли отдельно.** Пароль, попавший в публичный репозиторий, считается скомпрометированным навсегда — даже если удалить его следующим коммитом, он останется в истории и в кэше GitHub. Поэтому в репозитории лежат только шаблоны `.example`, а настоящие значения — в игнорируемых файлах.

Проверить перед первым push, что секреты точно не уедут:

```bash
git check-ignore -v stand/.env
```

Если команда что-то вывела — файл игнорируется, всё в порядке.

## Отправка на GitHub

Первый push делается с указанием ветки:

```bash
git push -u origin main
```

Ключ `-u` запоминает связь, дальше достаточно просто `git push`.

**Как происходит вход.** В системе настроен Git Credential Manager. При первом push он открывает окно браузера с формой входа GitHub. После входа токен сохраняется в хранилище Windows, и больше вход не потребуется.

Если окно не появилось, а в консоли висит запрос логина — значит helper не сработал. Проверить:

```bash
git config --system credential.helper
```

Должно вывести `manager`.

**Отправить в локальный репозиторий** (работает всегда, без интернета):

```bash
git push local main
```

## Если что-то пошло не так

| Ситуация | Команда |
|---|---|
| Отменить изменения в файле, не закоммиченные | `git checkout -- путь/к/файлу` |
| Убрать файл из индекса, оставив правки | `git restore --staged путь/к/файлу` |
| Исправить сообщение последнего коммита | `git commit --amend -m "Новое сообщение"` |
| Посмотреть, что именно изменилось | `git diff` |
| Посмотреть изменения в коммите | `git show <хеш>` |
| Вернуться к состоянию коммита (создав новый) | `git revert <хеш>` |

**Не делай `git push --force` в общий репозиторий.** Это переписывает историю на сервере и уничтожает чужую работу. В своём личном — допустимо, но привыкать не стоит.

**Главная страховка:** почти всё в git обратимо, пока изменения закоммичены. Команда `git reflog` показывает вообще все перемещения HEAD за последние недели, включая «потерянные» коммиты. Потерять закоммиченную работу довольно трудно — а вот незакоммиченную легко. Коммить часто.

## Упражнение

Чтобы закрепить, сделай цикл целиком:

1. Создай ветку `feature/my-first-test`.
2. Добавь в `AccountsListTest` ещё один поиск в `@ValueSource` — любую компанию из списка.
3. Запусти тест, убедись, что зелёный.
4. Закоммить с осмысленным сообщением.
5. Влей в `main` с `--no-ff`.
6. Запушь на GitHub.
7. Открой репозиторий в браузере и найди свой коммит.
