# Автотесты для локального стенда EspoCRM

Учебно-портфельный проект: UI + API + БД автотесты на Java. Стек намеренно повторяет рабочий проект `cometal` — что выучишь здесь, применимо там, и наоборот.

**Стек:** Java 21, Gradle 8.6, JUnit 5, Selenide, REST Assured, AssertJ, Allure, MySQL Connector/J, Lombok.

## Запуск тестов

> [!important] Все команды выполняются **из папки проекта**
> Запись `.\gradlew.bat` означает «файл в текущей папке». Если запустить её из `C:\Windows\System32`
> или из домашней папки, будет ошибка «Имя не распознано как имя командлета». Сначала перейди в проект:
>
> ```bash
> cd C:\Users\Evgeny\IdeaProjects\aqa-espocrm
> ```
>
> Проверить, что ты на месте: в папке должен лежать `gradlew.bat` (команда `dir gradlew.bat`).
> В IntelliJ IDEA встроенный терминал открывается в папке проекта сразу — там `cd` не нужен.

Все тесты:

```bash
.\gradlew.bat test
```

Отдельный класс:

```bash
.\gradlew.bat test --tests "ru.espocrm.smoke.EnvironmentSmokeTest"
```

Переопределить настройку на лету (системные свойства пробрасываются в JVM тестов):

```bash
.\gradlew.bat test "-Dselenide.headless=true"
```

## Отчёт Allure

Собрать отчёт в папку:

```bash
.\gradlew.bat allureReport
```

Готовый отчёт: `build\reports\allure-report\allureReport\index.html` — можно открыть двойным кликом.

Собрать и сразу открыть в браузере:

```bash
.\gradlew.bat allureServe
```

`allureServe` поднимает локальный веб-сервер и **не завершается сам** — консоль будет занята, пока не нажмёшь Ctrl+C. Это нормально, так и задумано.

Отчёт строится по результатам последнего прогона из `build\allure-results`. Если тесты ещё не запускались, отчёт будет пустым.

## Структура

```
src/test/
├── java/ru/espocrm/
│   └── smoke/EnvironmentSmokeTest.java   <- временный, удали когда напишешь свой первый тест
└── resources/
    ├── selenide.properties                таймауты, размер окна, скриншоты
    ├── junit-platform.properties          настройки JUnit
    ├── allure.properties                  куда складывать результаты
    └── env/
        ├── local.properties.example       шаблон (в git)
        └── local.properties               реальные значения с паролями (в .gitignore)
```

`env/local.properties` уже сгенерирован из `.env` стенда и содержит адрес, учётку админа и строку подключения к базе.

## Пошаговый план: что писать самому

Порядок не случайный: каждый шаг опирается на предыдущий. После каждого — показывай код, разберём.

### Шаг 1. Чтение конфигурации
Класс, который читает `env/local.properties` и отдаёт `url`, `adminLogin`, `adminPass`, параметры БД.
Аналоги в `cometal`: `ReadProperties` + `EnvConstants`.
*Готово, когда:* из теста можно получить адрес стенда, не зная, откуда он взялся.

### Шаг 2. BaseTest
Базовый класс: открыть браузер перед тестом, закрыть после, подключить `AllureSelenide` listener, задать `Configuration.baseUrl`.
Аналог в `cometal`: `BaseTest`.
*Готово, когда:* наследник класса получает готовый браузер и скриншот в отчёте при падении.

### Шаг 3. Первый UI-тест без Page Object
Залогиниться админом, убедиться, что попал в систему. Пока прямо в тесте, с локаторами внутри.
*Готово, когда:* тест зелёный. Заодно почувствуешь, почему так писать неудобно.

### Шаг 4. LoginPage
Вынести локаторы и действия в Page Object, тест переписать на него.
*Готово, когда:* в тесте нет ни одного селектора.

### Шаг 5. Списки и поиск
Тест на раздел Accounts: открыть, проверить количество строк, найти компанию по названию.
*Готово, когда:* тест не зависит от порядка строк и не падает на пагинации.

### Шаг 6. Создание и уборка за собой
Создать компанию через UI, проверить в списке, удалить через API в `@AfterEach`.
*Готово, когда:* после прогона в системе не остаётся мусора — как в нашем тесте для `cometal`.

### Шаг 7. Слой Steps
Вынести бизнес-действия в отдельный слой с `@Step`, тесты станут из 3-5 строк.
Аналог в `cometal`: пакет `steps`.
*Готово, когда:* в отчёте Allure читается сценарий, а не клики.

### Шаг 8. API-тесты
REST Assured: авторизация, создание/чтение/удаление сущности, проверка кодов ответа и тела.
*Готово, когда:* есть позитивные и негативные проверки (401, 400, 409 — мы их все видели на этом стенде).

### Шаг 9. Проверки в базе
JDBC: после действия в UI сверить данные в MySQL. Не забудь `WHERE deleted = 0` и обратные кавычки для таблицы `` `lead` ``.
*Готово, когда:* тест ловит расхождение между интерфейсом и базой.

### Шаг 10. Зрелость
Параметризованные тесты, теги для групп прогона, параллельный запуск.
*Готово, когда:* разобрался, почему при параллельном запуске важен `ThreadLocal` в Selenide.

### Шаг 11. Публикация
Выложить на GitHub, настроить GitHub Actions, добавить в README скриншот отчёта.
*Готово, когда:* ссылку не стыдно положить в резюме.

## Git

Репозиторий уже инициализирован локально — удалённый сервер для работы не нужен:

```bash
git status
git add .
git commit -m "Шаг 1: чтение конфигурации"
git log --oneline
```

Коммить после каждого шага плана: будет видна история роста, и это тренировка той же работы с ветками, что и в `cometal`.

Когда проект созреет для портфолио — создашь репозиторий на GitHub и добавишь remote:

```bash
git remote add origin https://github.com/<твой-аккаунт>/aqa-espocrm.git
git push -u origin main
```

`.gitignore` уже настроен: сборка, настройки IDE, отчёты и `env/local.properties` с паролями в репозиторий не попадут.
